# SERV setup and live verification

**Current state:** local example mode works. One real SERV API response for the included synthetic fixture passed local validation on 27 September 2026; the console marked that response as a **cache hit**, so fresh upstream inference is not established by it. Two prior one-call attempts returned no accepted report. The redacted success proof and normalized report are in [`evidence/`](evidence/). API key handling remains with the operator. Training/data-collection opt-in was off or pending; no hackathon entry or eligibility is claimed.

1. Review the OpenServ account terms and actual credit/billing settings before any new live request. The [hackathon instructions](https://www.openserv.ai/hackathon) also require data collection enabled in [organization settings](https://console.openserv.ai/settings/organization) for eligibility. The published verification does not establish that setting or entry status.
2. Generate a SERV API key in the console, as described by the [API overview](https://docs.openserv.ai/serv-reasoning/api). Set it as `SERV_API_KEY` in the local server process environment without putting it in project files, a public issue, a screenshot, or a command argument. Restart the server. `GET /api/status` should then show `live_enabled: true` without exposing the key.
3. The default model is `gpt-6-luna`, listed in the [official model catalog](https://docs.openserv.ai/serv-reasoning/models). An operator may set `SERV_MODEL` to another catalog ID before starting the process. The fixed endpoint and supported request fields come from the [chat completions reference](https://docs.openserv.ai/serv-reasoning/api/chat-completions). The request includes a strict JSON response schema for all 12 extraction fields; the local validator still rejects unsupported quotes or values.
4. Paste only public or synthetic listing text and its HTTPS source URL. Review the text for credentials and private buyer data, then check the consent box. Submit once. The app makes one bounded call, with no retries. A successful report must display **LIVE SERV MODE**, the actual model ID, exact validated quotes, and a new input hash. A synthetic report must keep **EXAMPLE MODE** and say no SERV call.
5. Review any `SERV_HTTP_ERROR` by status category: 400 often means model/parameter mismatch; 401/403 means key or access; 402 means credit/payment; 404 means path/model; 429 means rate limiting; 5xx means provider failure. `MALFORMED_EXTRACTION_JSON`, `UNSUPPORTED_SERV_RESPONSE`, `SERV_OUTPUT_TRUNCATED`, and `EVIDENCE_REJECTED` mean no report was accepted. The app does not echo raw provider bodies or retry automatically.
6. Save a redacted verification record with timestamp, model, report mode, and validation result. Keep the key and full prompt out of public screenshots and submission text. The included verification is a successful SERV API response marked cache hit, not a full browser UI live-flow capture.

The source URL is provenance supplied by the operator, not a fetched or authenticated page. Even a successful live response validates quote presence only. Check buyer terms, current award capacity, fee currency, eligibility, and payout timing separately before investing effort.
